## 测试期间修正

- 复现失败基线可作为阶段成功的证据；必须由验收器显式声明预期失败，普通失败测试不会自动通过。
- 同一行的编号与任务内容保持关联，旧会话的原验收 ID 保持不变。
- 规划缺少原目标或依赖无效时提供一次有界纠错，不直接无限重试。
- 后续阶段的测试和读回证据可以验收前面阶段的目标，仍拒绝未知引用。
- 规划避免把小修复拆成重复探索、实现、接入等过多阶段，并提示保留验收预算。
- `fs.read.startLine` 支持直接读取搜索行号附近的代码，避免猜测字节偏移；中文、CRLF、跨缓冲区、EOF、扫描上限和预取消已测试。
- Pulse 自己修复 `fs.search` 摘要静默丢弃：保留最多 20 条结果，同时提供 `shown`/`omitted` 和原搜索统计，区分摘要省略与搜索截断。

## 尚不能宣称的能力

这次开发需要多轮续跑和外部指导；早期重复读取耗尽预算，首次执行成功率与 token 效率仍不理想。
已结束运行的续跑会重新规划，尚不等同于中断快照恢复时直接保留已完成阶段。
脏工作区的修改归因本次依靠外部提取的三轮工具记录；还没有自动化的完整任务级工作区基线审计。
历史运行的测试引用也不能直接冒充本轮 ResultRef。一次续跑同时要求“不重复测试”和
“本轮测试证据”，导致内部审批拒绝重跑；后来明确允许两条指定验证命令才继续。
这说明跨运行证据的安全复用仍需改进，不能仅靠模型复述历史结果。

本轮没有 Windows/Linux 实机结果、所有真实 MCP 服务、24 小时运行或完整 72 次质量评测。
搜索实现审查指出的读取中取消、文件增长读取上限、内部符号链接问题仍是单独的后续代码任务，
本轮实际自开发修复只涵盖搜索摘要。

当前适合从范围明确、有测试、有外部代码审查的小型开发任务开始。
不要把本次可恢复且可审查的开发闭环描述成无人值守的成熟自开发系统。
