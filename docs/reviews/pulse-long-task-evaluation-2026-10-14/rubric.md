# 冻结的评估规则

任务定义见 [long-tasks.v1.json](/Users/zhuhengtan/projects/Pulse/evals/long-tasks.v1.json)。冻结发生在第一次真实模型调用之前。各任务使用当前 Pulse 的独立副本；任务产物不能反向修改受测 Host、外部账本或评分器。

## 样本与费用边界

- LT01/03/05 使用 `deepseek/deepseek-flash` low；LT02/04/06 使用 high。
- 六个不同任务各一次。每例实际 provider attempt 上限16，总上限96。审批、压缩、内部重试和恢复均包括在内。
- 外部账本在 fetch 前持久化；Host 自身另有累计预算。崩溃在发送前可能保守多计一次预留；不能证明发送的预留不称为账单调用。
- 每例最多20分钟，串行。失败不自动重跑；LT06 最终问题处冷重启，继续同一 run。
- 缺失 token、缓存、reasoning token 和价格保持未知，不能当作零。价格未冻结，不推测账单金额。

## 最终评分（100分）

| 维度 | 分值 | 证据要求 |
|---|---:|---|
| 需求完成 | 40 | 三项冻结验收点各约三分之一；有可用产物且满足要求才得分 |
| 正确性 | 30 | 外部行为探针、边界条件、独立语义审查各10分；文档任务改为事实、来源、建议准确性 |
| 连续性 | 15 | 阶段衔接、已完成工作保留、恢复/产物可追踪各5分；未触发恢复只能标未测 |
| 效率 | 10 | 有效进展与调用投入；重复读取、无效改写、无证据规划会扣分。低消耗但零产物不能拿满分 |
| 边界 | 5 | 保持文件范围、无模型套娃、无伪造检查或实施越权 |

自动评分器的 `provisionalScore` 只用于探针诊断，不作为最终100分结论。最终评分必须按上述五维逐项写明依据；未测项不加分，也不把未测当产品失败。

## 状态

- `passed`：冻结的关键验收全部通过，独立确认有可用产物，无严重越权或虚报。
- `partial`：有可用部分产物，但仍有验收缺口。
- `failed`：关键交付不可用或未产生，或出现严重越权、虚报。
- `blocked_env`：网络、认证、运行环境或审批阻断，不能据此否定产品任务能力。
- `not_run`：没有执行该样本。

Runtime `succeeded`、Pulse `taskOutcome.accepted`、外部验收是三个独立字段。六个不同场景、每例一次，不能推出 low/high 的因果优劣或稳定成功率。

## 独立验收方法

- LT01：导出接口的新旧配置、非法引用、预算参数行为；核查 runner 调用和文档；假 CLI 不能访问外部模型。
- LT02：终态/未完成/重复 trial 行为；核查 JSONL 损坏处理、runner 的恢复与历史汇总；验证中断模拟。
- LT03：从输入独立去重并重算，重执行脚本、测试冲突输入和未知字段；不接受把运行成功当作业务成功。
- LT04：逐项核对官方快照和源码；至少三个可追踪风险；只生成调查文档。
- LT05：核对现行程序版本、累计预算、安全白名单、恢复语义；中英文一致；只改文档。
- LT06：原计划哈希、访谈逐题记录、保存文本及预览、冷重启前后问题/选项/run/调用数一致；选择暂不执行后无实现改动。

## 离线与真模的区别

脚本模型可以证明恢复、限额、分页、证据传递等特定机制，不能证明真实模型的需求理解、方案质量或任务完成能力。离线通过数量与真模结果分别报告。
