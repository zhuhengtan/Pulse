# 问题及优化顺序

## P1：离线检查准备进入审批，阻断完整交付

第30次请求执行 `node scripts/eval/.verify-resume/make-dataset.mjs`。它是任意 Node 脚本，不属于现有必要检查规则；评测未配置本地 reviewer，原生人工确认按无 blanket approval 规则拒绝。后续 git 只读提议受同一个运行错误阻断，未执行。此处不能称为有效测试命令被误拒，也不能通过免审任意 Node 脚本解决。

建议：在任务开始前展示当前可用检查入口和审批能力，优先将夹具准备及假 CLI 集成写成自包含的 `.test.mjs`，使用已有必要检查入口。若确需任意脚本执行，必须正常审批；评测无人工授权时明确环境/权限阻塞。不要换等价命令绕过拒绝。

## P1：候选仍未实现重复历史终态汇总去重

独立探针仍得到 tasksRun=3，应为2。候选只在待执行选择中去重，报告的 records 直接保留全部原始历史行。任务是否重跑、汇总是否重复是两个不同的验收点。

建议：原始 JSONL 字节保留，另建按 taskId/trial 的规范终态视图，用于汇总和预算；测试重复成功、失败、冲突和非终态记录。当前主工作区 runner 已有相关修复；本轮故意从原始缺陷输入独立生成，不能用主工作区修好替代模型候选验收。

## P1：候选恢复时重置未知费用状态

`consumedCostUnknown=false`，历史 providerCosts 缺失状态未继承。独立探针得到2次假 CLI 调用，应为1次。token 上限继承通过，并不代表费用边界同时正确。

建议：复用一致的历史用量视图，未知费用在配置费用边界时继续阻止新增任务；未知不能填零。覆盖首次停止、恢复、重复记录和不同币种。

## P1：恢复未完成 trial 时覆盖原有夹具文件（新诊断已复现）

候选 runner 使用 `flag: has('--resume') ? 'w' : 'wx'` 重新写入 fixtures。补充离线探针在待恢复 trial 预先保存 `USER EDIT MUST SURVIVE`，恢复后变成 `ORIGINAL FIXTURE`，证明已有同名用户文件被覆盖。冻结九项中的中断探针只覆盖另一个新建用户文件，未覆盖原始夹具同名编辑，因此7/9仍保持原样，没有事后改评分。

建议：恢复仅创建缺失夹具；已有文件保留。若需重置必须单独明确操作，并校验恢复的 dataset/fixture 身份；补充“初始夹具被用户修改后崩溃”的探针。

## P2：最终失败详情重复八次、标准映射过粗

冻结9项检查中7项通过，但 evaluation-resume-contract 的两个失败被复制到8条 criterion 全部标为 not_met，同样详情在最终正文重复8次。已有失败不再遗漏，这是改善；逐条归因和简洁性仍不够准确。

建议：检查断言显式映射到对应 criterion；共享失败详情只显示一次，各标准引用它。保留已证明通过的断言与证据，对缺证据标 unverifiable，而不是把整个检查组失败等同每条业务标准失败。仍不能把整体任务判成功。

## P2：阶段检验偏局部，重复读取仍增加消耗

runner 阶段在语法检查和文本查看后通过，实际未知费用、重复汇总、原夹具保存语义留到最终才被发现。请求15还在同一批中重复读取完全相同分页。没有发生重新规划或四轮空转，但仍有优化空间。

建议：编辑阶段将风险项绑定到早期离线行为断言，阶段通过后继续沿用其证据；同批完全相同、文件版本一致的读取共享结果。不要因为一次重复读取误触发循环停止或阻断合法分页。
